# Arquitetura

```
 agente (Claude Code, Cursor…)            humano (navegador)
        │ MCP stdio | Streamable HTTP /mcp        │ WebSocket /ws
        ▼                                         ▼
 ┌──────────────────────── server (paprika) ────────────────┐
 │ MCP (JSON-RPC) ──┐                       ┌── API HTTP + /ws  │
 │                  ▼                       ▼                   │
 │        Store  (internal/core: applyOps + History, SQLite)    │
 └───────────────────────────┬─────────────────────────────────┘
                             ▼
                    paprika.db (SQLite) ── import/export ── design.paprika.json (git)

 ┌──────────────── @paprika/core (TypeScript) ─────────────────┐
 │ schema (zod) · applyOps (transação) · History (undo/redo)    │
 │ nodeStyle → canvas React · renderHTML · exportReact          │
 │ lintDocument · outline/queryNodes      (referência do Go)    │
 └──────────────────────────────────────────────────────────────┘
```

## Decisões

1. **Mapa plano de nós + `children` em contêineres (`frame`, `group`, `page`).** Acesso O(1) por id para o agente, árvore explícita para render. `parseDocument` valida integridade (sem órfãos, sem duplicados, `parentId` coerente, páginas só no topo e, havendo uma página, só páginas no topo).
2. **Uma única porta de escrita: `applyOps`.** Canvas, MCP e `POST /api/ops` geram as mesmas operações. A transação roda num clone e só substitui o documento se todas as operações passarem. Cada transação gera as operações inversas, que alimentam o undo/redo compartilhado.
3. **Rejeitar campos desconhecidos.** Zod descartaria em silêncio (`colour` em vez de `color`); para agentes, um erro explícito é mais barato que um design errado.
4. **Um motor de estilo.** `nodeStyle` gera o CSS usado pelo canvas, pelo HTML do screenshot e pelo export React. O que o agente confere no PNG é o que o humano vê. Para nós `path`, `pathAttrs` faz o mesmo papel para os atributos de `<svg>`/`<path>`, e `packages/core/src/path.ts` (parser, normalização, caixa exata de bezier e arcos) roda igual no servidor, no canvas e nos testes; `d` inválido é rejeitado com a posição do caractere.
5. **SQLite é a fonte da verdade.** Documentos, tokens e o histórico de undo/redo ficam no SQLite ([ADR 0001](adr/0001-servidor-go-sqlite.md)); cada mudança é uma transação gravada antes da resposta. O `.paprika.json` entra e sai só por `paprika import`/`export`.
6. **MCP HTTP stateless.** Sem estado de servidor por conexão para vazar (o `Mcp-Session-Id` só carrega o nome do cliente); o estado vive no store. As ferramentas de escrita só respondem depois da gravação.
7. **Local primeiro.** Bind em loopback com validação de Host/Origin. Sem autenticação nem multiusuário nesta versão.
8. **Operações compostas se expandem dentro da transação.** `group`, `ungroup` e `add_page` também são operações, mas o `applyOps` as transforma em create/move/update/delete contra o documento *como ele está naquele momento* (`packages/core/src/structure.ts`): um canvas ou agente com uma cópia um pouco velha ainda recebe o resultado certo, numa só entrada de desfazer. A caixa de um grupo é derivada: no fim de cada transação o `fitGroups` ajusta cada grupo aos filhos (do mais fundo para o mais raso) e os desloca para nada se mover na tela; a inversa só guarda posições, e `width`/`height` de grupo são recusados na entrada.
9. **Instâncias são cópias derivadas.** Um componente é um frame com `component: true`; pode declarar `componentProps` (`text`, `boolean`, `variant`) e conter frames ou groups com `slot`. Uma instância é um frame com `instanceOf`, `scale` opcional, `propValues`, `slots` e `overrides` (por id de nó do componente ou pelo caminho `instancia/copia`, só `fill`, `color`, `text`, `src`, `alt`, `visible`, `opacity` nas cópias; `fill` na raiz; `propValues` e `slots` num caminho de instância aninhada). Um nó dentro do componente pode `bind` uma prop de texto ao texto, uma boolean a `visible`, ou um mapa de variante que omite o nó salvo quando cada par combina (um par pode listar várias opções, e qualquer uma combina; no próprio componente só a variante padrão é desenhada, as outras ficam ocultas no documento; checado no fim da transação, então um componente e seus filhos com `bind` podem nascer numa só chamada). O conteúdo de um slot clona nós existentes para dentro dele. Instâncias podem ser aninhadas; um ciclo é recusado. No fim de cada transação o `syncInstances` (`packages/core/src/component.ts`) checa as regras e refaz os filhos de cada instância a partir do componente, com ids determinísticos (`copyId`, FNV-1a de instância + id de origem, igual no Go) e `sourceId` em cada cópia. As cópias são nós comuns, então renderizadores, export e lint funcionam sem mudança; como são derivadas, o desfazer nunca as guarda: desfazer a mudança no componente ou na instância e sincronizar de novo basta. Um `update` numa cópia vira override na instância mais externa, com a chave do caminho juntado; mover, apagar ou criar filhos dentro de uma instância é recusado. `detach` transforma a instância num frame comum com os mesmos ids, descartando o `bind` das cópias. `detach_tokens` numa instância ou cópia só mexe nos overrides que ela possui e informa os campos derivados que pulou.
10. **Import e export SVG são funções puras no core.** `importSVG` e `importHTML` (`packages/core/src/svgImport.ts`, `htmlImport.ts`, sobre um leitor tolerante em `markup.ts`) devolvem árvores `NodeInput` mais `warnings`, e quem chama grava com ops `create` comuns, então colar é um passo de desfazer e passa pela mesma validação. O `importSVG` transforma `<text>` em nós de texto e expande sprites `<use>`/`<symbol>`; imagens, gradientes, máscaras e `<style>` continuam avisos. `importHTML` é o inverso do `nodeStyle`: o HTML do `renderHTML` (que marca cada elemento com `data-paprika-type`) volta com os mesmos tipos e campos. A função pura só lê estilos inline. O `import_html` com `computed: true` é só no servidor: o handler Go renderiza o HTML no Chromium, grava os estilos computados do autor inline e então chama o mesmo `importHTML`. Chromium ausente é erro, sem fallback. `exportSVG` monta o SVG a partir das caixas do `layout(doc)` do core (layout automático, `hug`/`fill`); o texto quebra em `\n` (quebra por glifo continua aproximada). Um `Measure` opcional ainda sobrescreve caixas e linhas nos goldens e caminhos legados; o `MEASURE_SCRIPT` permanece para isso.
11. **Presença do agente é implícita e efêmera.** O agente não chama uma ferramenta de presença: toda chamada MCP que chega ao handler reporta `{agent, actor, tool, nodes}` ao `PresenceHub` do store (`server/internal/server/presence.go`), e o `/ws` difunde como `{type: "presence", agent, actor, tool, nodes, idle}`. `nodes` são os ids que a chamada criou ou, se nenhum, os ids citados nos argumentos (que ainda existem); `agent` é um hash do `Mcp-Session-Id` do HTTP (duas sessões do mesmo cliente são dois agentes) ou o ator no stdio. A presença nunca toca o documento, o histórico nem o disco; um canvas que conecta recebe, logo depois do documento, a última presença de cada agente dos últimos 2 minutos. O canvas mede os nós no DOM (então layout automático e `hug` ficam certos) e desenha cursor, contorno e lista (`apps/web/src/AgentCursors.tsx`). Os nós que um agente cria nunca ficam escondidos nem pela metade: o documento os mostra de uma vez, e o cliente só passeia o contorno do agente pelos ids criados (`BuildReplay` em `agents.ts`, um passeio por ator, no máximo cerca de 2 s por escrita, nenhum com `prefers-reduced-motion`).

11. **Workspace = documento, um ativo por servidor.** A página inicial lista os documentos do banco do servidor. O `Store` mantém um documento ativo; `openWorkspace` troca esse documento no lugar e emite uma mudança com kind `open`, então o WebSocket, a API HTTP e toda ferramenta MCP acompanham sem encanamento novo. Canvas e agentes compartilham o workspace ativo de propósito: o humano vê o que o agente edita. Uma aba do canvas em `/w/<id>` é a exceção: ela envia `{type:"view", workspaceId}` pelo WebSocket e o servidor roteia o documento, as edições e o desfazer dessa conexão para aquele workspace (`ApplyIn`/`StepIn`, com eventos `OnAside` para um workspace que não é o ativo), então abrir uma URL nunca troca o workspace ativo; uma conexão sem view acompanha o ativo. O histórico de undo é de cada workspace e fica gravado no SQLite, então sobrevive à troca. O workspace ativo é por processo: um `paprika mcp` separado via stdio mantém o seu.
12. **Conectores de diagrama derivam das pontas.** Um nó `shape` (rect, ellipse, diamond, triangle, cylinder, parallelogram, cloud, note) é uma caixa com texto dentro, pintada por `shapeAttrs` (um contorno `<svg>` atrás do texto, igual no canvas, screenshot, React e export SVG). Um `connector` guarda só as pontas (`from`/`to`: um `nodeId` com lado opcional, ou um `x`/`y` livre nas coordenadas do pai), a rota (`straight`, `elbow`, `rounded` com `radius`, ou `curve` com `control` opcional) e a aparência; `x`, `y`, `width`, `height` e `d` são recalculados por `routeConnectors` (`packages/core/src/diagram.ts`) no fim de toda transação, depois da sincronização das instâncias, e são recusados na entrada. Como as cópias de instância, essa geometria não guarda inversa. As pontas são cortadas no contorno da forma usando só `sqrt` (sem trigonometria), então o port em Go dá os mesmos números. Apagar um nó apaga, na mesma operação, os conectores presos a ele (o desfazer traz os dois), e um conector nunca conta na caixa do grupo. `draw_diagram` é uma função pura do documento (`diagramOps`): ordena as formas pelo caminho mais longo (arestas de volta, achadas por DFS, não contam), centraliza cada camada e devolve operações `create` comuns. Conectores em cotovelo e arredondados desviam das caixas de outras formas no mesmo pai, com 8px de folga; rotas retas e em curva não. `relayout: true` aceita ids de formas que já existem e devolve operações `update` (`x`/`y` quando vierem, senão o `x` atual) para essas setas serem recalculadas no mesmo passo de desfazer.

13. **Constraints acompanham o redimensionamento do pai.** Um nó de cena (não uma página nem um conector) pode definir `constraints: { horizontal: left|right|center|scale, vertical: top|bottom|center|scale }`. Omitir significa left e top, o comportamento anterior. No fim da transação, antes de `fitGroups` e `syncInstances`, um frame cuja largura ou altura numérica mudou move ou escala cada filho fora do fluxo (o frame não está em linha/coluna, ou o filho tem `layoutPositioning: "absolute"`). `left`/`top` mantêm a caixa, `right`/`bottom` mantêm a margem do lado oposto, `center` mantém a distância ao centro do pai, e `scale` multiplica x/y e a largura/altura numérica pela razão do tamanho do pai. A conta usa a caixa gravada, não os limites rotacionados. `hug`/`fill` continuam como estão (só a posição escala). Um frame cujo próprio tamanho é `fill` ou `hug` (num eixo que também não era numérico antes) também reposiciona seus filhos fixados fora do fluxo, pela variação do tamanho calculado: o passo compara as caixas do motor de layout antes e depois da transação, então um frame fill numa coluna recebe o delta inteiro do ancestral redimensionado e um numa linha recebe sua parte do espaço livre. A constraint scale de um grupo escala as caixas dos descendentes até um frame aninhado, cujos filhos então seguem as próprias constraints. A largura e a altura de uma instância continuam no componente, então scale na instância só a move. Os ajustes são derivados, como a geometria dos conectores: desfazer redimensiona o pai e o passo roda de novo. O inspector mostra os dois eixos nesses filhos.

14. **`/ws` envia mudanças, não o documento inteiro.** Uma conexão recebe um snapshot completo `{type:"doc", doc, version, actor, label, kind, canUndo, canRedo}` ao abrir, depois de `view` (e quando o servidor troca o workspace ativo ou recarrega do banco) e quando fica para trás. Toda outra escrita é um delta: `{type:"delta", id, version, base, actor, label, kind, canUndo, canRedo, name?, rootIds?, nodes?, tokens?, modes?, tokenMeta?, assets?}`. `id` é o workspace, `base` é a versão sobre a qual o delta se aplica (sempre `version - 1`) e cada patch de mapa é `{set?: {chave: valor}, del?: [chave]}`: `nodes.set` traz o valor novo de cada nó alterado ou criado (um id removido vai em `nodes.del`); `rootIds` e `name` só aparecem quando mudaram. O servidor acha a mudança enquanto grava a escrita (`writeDocument` já compara o documento anterior e o novo linha a linha), então o delta não custa uma passada extra pelo documento. Quando a mudança não cabe nesse formato (um mapa que aparece ou some, ordem de chaves inesperada, `open`, `reload`, importação) o evento não leva delta e o servidor manda um snapshot. A fila por conexão (`wsoutbox.go`) nunca junta nem descarta um delta: eles esperam em ordem atrás do slot do documento. Um snapshot no slot substitui os deltas pendentes até a sua versão, e os deltas depois dele se aplicam por cima. Quando mais de 256 deltas ou 2 MiB ficam pendentes numa conexão, ou um delta deixaria um buraco, eles viram um snapshot novo em vez de fechar a conexão. O canvas só aplica um delta quando `base` é igual à versão aplicada e o workspace é o mesmo; senão reenvia `view` para receber um snapshot (`apps/web/src/docDelta.ts`, `useDocument.ts`). Aplicar um delta copia o mapa `nodes` mas mantém a identidade de todo nó intocado, e os ids alterados e criados vêm da mensagem, sem serializar nada para descobri-los. Clientes que só entendem `doc` precisam enviar `view` depois de cada `delta` para continuar funcionando; o canvas, os helpers de e2e e a suíte de performance entendem os dois.

## Servidor e core

O `server/` é o único servidor; o servidor TypeScript do qual ele foi portado foi removido. O `server/internal/core` é um port do `@paprika/core`, que o canvas roda e que continua sendo a referência: fixtures geradas a partir do core TypeScript (`pnpm go:golden`) travam o port Go byte a byte. O contrato MCP (definições das ferramentas, instruções) é o `server/contract/mcp.json`, servido como está; o `packages/e2e` confere o binário por fora (MCP, HTTP, WebSocket, canvas).

**Camada HTTP.** O `StartHTTP` monta o canvas, `/api/*`, as rotas de time, `/ws` e o Streamable HTTP `/mcp` no [Gin](https://gin-gonic.com/) (`gin.New()`, modo release, proxies confiáveis desligados). A recuperação de panic e a checagem de Host/Origin (`AllowedRequest`) rodam como middleware antes de toda rota, inclusive 404. O `/ws` continua com `github.com/coder/websocket` dentro de um handler Gin; `team.Service.Routes` recebe um router Gin. O protocolo MCP (`MCP.Handle`, ferramentas, schemas) e o stdio (`ServeStdio`) ficam fora do Gin.

## Limitações conhecidas (v0.1)

- Dois processos no mesmo banco (`serve` + `mcp`) enxergam as gravações um do outro em ~300 ms, mas cada um mantém o seu workspace ativo. Para usar MCP e canvas juntos, prefira `paprika serve` + MCP HTTP.
- Sem operações booleanas entre paths, edição ponto a ponto de paths no canvas (a caneta cria paths novos; os existentes se editam pelo `d`) ou rotação no hit-test do canvas.
- Grupos não têm rotação própria (gire os filhos), e filhos com tamanho `hug`/`fill` contam como um ponto no ajuste da caixa. Nós dentro de um frame row/column não podem ser agrupados (a posição vem do fluxo).
- `layout()` segue o `flex-wrap` como o `nodeStyle` o emite: os itens ficam numa linha enquanto cabem (`fill` conta como largura 0), cada linha tem a altura do seu item mais alto e as linhas dividem por igual o espaço de sobra no eixo cruzado (`align-content` fica no padrão do CSS), `justify` e `align` valem por linha, e um único `gap` é o espaçamento entre colunas e entre linhas. Uma row com largura `hug` nunca quebra (`max-content` do CSS); um frame com `wrap` precisa de largura fixa, ou de `fill` dentro de um pai que tenha, para quebrar linhas. Encolhimento flex e alinhamento por linha de base não são modelados.
- `scale` não escala um `fontSize` que é token.
- O lint de contraste ignora gradientes e imagens de fundo.
- A presença do agente só chega aos canvas do mesmo processo: um `paprika mcp` (stdio) cuja porta estava ocupada roda sem canvas, então o cursor dele não aparece no canvas do `paprika serve`. Use MCP via HTTP para ser visto.
- O import de SVG ignora texto, imagens, gradientes/padrões (viram cinza), máscaras, clip paths e CSS de `<style>`; o import de HTML só lê `style=""` inline (sem classes nem folhas de estilo). O export SVG deixa de fora strings de gradiente CSS e imagens de fundo, emite um `gradient` estruturado (linear e radial como gradiente SVG, cônico como `foreignObject`), desenha sombras sem spread, omite sombra interna com um aviso e usa `layout(doc)` (sem Chromium headless); a quebra de texto por glifo é aproximada.
- Fontes: um `fontFamily` sem família genérica (`serif`, `sans-serif`, `monospace`, ...) ganha uma no `nodeStyle` (sans-serif, a não ser que o nome pareça serifado ou mono), então uma fonte ausente nunca cai na serifa padrão do navegador. A Inter que o export embute também é servida pelo servidor Go (`/fonts/inter.css`, `/fonts/Inter-*.ttf`) e injetada nos screenshots, então `Inter` fica igual no canvas, no `render_screenshot` e no `export_image`. As demais famílias ainda dependem da máquina.
- Arrastar no canvas só move nós em pais sem layout automático (em row/column a ordem vem do layout).
